# Garmin Trends — Visualization Plan

Status: planned. Not yet implemented.
Owner: Stanley
Date: 2026-07-16

---

## 1. Goal

Replace the existing single-year, single-metric Garmin trend page with a richer, more controllable visualization that:

- Refactors and hardens the existing data pipeline (`get-garmin.py`, 1120 lines).
- Cleans the data with explicit, auditable drop rules (extreme pace, junk distance/HR, non-running activity types).
- Adds a year-range overlay (each year plotted as its own series).
- Adds a distance-bucket filter (`<3`, `3-5`, `5-10`, `10-15`, `15-25`, `25-40`, `40+`, `all`).
- Plots pace and distance together on a dual Y-axis, with toggles to show one or both.
- Switches between line and bar chart on the fly.
- Auto-scales each Y-axis to a tight fit so the data fills the chart area.
- Looks professional and is easy to control.

**Privacy model.** This dashboard is intended to be public-readable (Netlify static site). What is exposed:

- Masked Garmin username (cosmetic only — first letter + `***`; no domain). Masking is for appearance, not anonymity; the JSON payload and Excel both contain enough data (per-activity dates, distance, pace) to identify the runner. Treat the dashboard as fully public.
- Aggregated monthly metrics per year are also exposed via the chart.
- The full per-activity array in `garmin_activities.json` includes dates, distance, pace, HR. This is also public. **Privacy assumption:** the dataset owner accepts that running dates + distances + pace are public information when they publish the dashboard. If that assumption changes, the JSON should not be deployed.

## 3. Data Model & Cleaning Rules

### 3.1 Per-activity record (after cleaning)

```json
{
  "date": "2024-03-15",
  "month": 3,
  "year": 2024,
  "distance_km": 12.34,
  "pace_s_per_km": 285,
  "duration_s": 3519,
  "avg_hr": 158,
  "max_hr": 174,
  "calories": 980,
  "elevation_m": 86,
  "vo2max": 52,
  "activity_type": "running"
}
```

All numeric fields except `year` and `month` may be `null` after cleaning.

### 3.2 Distance buckets

| Bucket | Range (km) |
|---|---|
| `<3` | `0 ≤ d < 3` |
| `3-5` | `3 ≤ d < 5` |
| `5-10` | `5 ≤ d < 10` |
| `10-15` | `10 ≤ d < 15` |
| `15-25` | `15 ≤ d < 25` |
| `25-40` | `25 ≤ d < 40` |
| `40+` | `d ≥ 40` |
| `all` | default — no filter |

### 3.3 Drop rules

Applied in this order; each emits a reason so the CLI can print a breakdown. Drop checks use the **raw meters / raw seconds** from Garmin (no rounding), so a 499 m activity does not get falsely passed by a 2-decimal round-up.

1. `date` is unparseable → drop · reason `date`
2. `activity_type` does not match the activity-class allow-rule → drop · reason `type`
3. `distance_m < 500` or `distance_m > 200_000` → drop · reason `distance`
4. `duration_s < 60` or `duration_s > 12 h` → drop · reason `duration`
5. `avg_hr < 30` or `avg_hr > 230` → drop · reason `hr`
6. `pace_s_per_km is None` → drop · reason `no_pace`
7. `pace_s_per_km` outside the **class-specific pace band** (see below) → drop · reason `pace`

**Activity-class allow-rule.** An activity is kept if its `activity_type` matches any of (case-insensitive, substring match against the Garmin `activityType` enum):

- starts with `run` (catches `running`, `trail_running`, `track_running`, `street_running`, `indoor_running`, `treadmill_running`, `virtual_run`, `ultra_run`, etc.) — class `run`
- equals `walking` or starts with `walk` — class `walk`
- equals `hiking` or starts with `hike` — class `hike`

Everything else (cycling, swimming, skiing, strength, yoga, …) is dropped. Future Garmin enum additions are picked up automatically if the substring rule matches.

**Pace band by activity class.** Running has a tighter band than walking/hiking because real-world hike pace is 15:00–25:00 / km and a 15:00 / km ceiling would drop virtually every hike. Bands:

| Class | Pace range (s / km) | Equivalent |
|---|---|---|
| `run` | `225 ≤ pace ≤ 900` | 3:45 – 15:00 |
| `walk` | `225 ≤ pace ≤ 1500` | 3:45 – 25:00 |
| `hike` | `225 ≤ pace ≤ 1800` | 3:45 – 30:00 |

A `pace_s_per_km` below 3:45 / km is dropped for any class (implausibly fast — sensor glitch, vehicle, GPS spike).

### 3.4 Aggregate payload (`garmin_activities.json`)

```json
{
  "meta": {
    "generated_at": "2026-07-16T10:32:00Z",
    "garmin_username_masked": "s***",
    "activity_count_after_clean": 1247,
    "activity_count_dropped": { "no_pace": 3, "pace": 12, "distance": 0, "hr": 3, "duration": 1, "type": 14, "date": 2 },
    "year_range": [2019, 2026],
    "distance_buckets": ["<3","3-5","5-10","10-15","15-25","25-40","40+","all"],
    "params": ["pace_s_per_km", "distance_km_total", "avg_hr", "duration_s", "activity_count"]
  },
  "activities": [ /* per-activity records, sorted by date ascending */ ],
  "monthly": {
    "by_year": {
      "2024": {
        "pace_s_per_km":     [null, null, 285.0, 290.1, null, null, 278.4, null, null, null, null, null],
        "distance_km_total": [12.3, 18.0, 22.5, 35.2, null, 42.1, 8.0,  15.6, 18.4, 20.1, 32.7, 24.0],
        "avg_hr":            [...],
        "duration_s":        [...],
        "activity_count":    [3, 4, 5, 6, 0, 7, 1, 3, 4, 5, 6, 4]
      }
    }
  },
  "monthly_by_bucket": {
    "2024": {
      "5-10": { "pace_s_per_km": [...], "distance_km_total": [...], "activity_count": [...] },
      "10-15": { ... },
      ...
    }
  }
}
```

Front-end gets `monthly.by_year` (already aggregated) → cheap `Plotly.react` on every filter change.

## 4. Front-end Behaviour

### 4.1 Layout (top → bottom)

1. **Header** — title + 4 summary cards: Total activities, Total years, Last refresh (ISO date), Garmin user (masked).
2. **Control bar** (sticky on scroll) — one row of segmented controls and chips:
   - **Year range** — dual-handle slider spanning `[min_year, max_year]`. Labels "From 2022 / To 2025". An "All years" pill resets. **Implementation note:** HTML5 `<input type="range">` does not support dual handles natively. The implementation must either (a) pull in a dual-handle library (e.g. `noUiSlider`, vendored or via CDN), or (b) build a minimal two-`<select>` fallback. The choice is made in Phase 3, not Phase 0; the front-end must not assume which one shipped until then.
   - **Distance bucket** — chip group: `<3 | 3-5 | 5-10 | 10-15 | 15-25 | 25-40 | 40+ | All`. Default `All`.
   - **Metric visibility** — two checkboxes: `Show pace` and `Show distance`. Both on by default.
   - **Chart mode** — `Line | Bar` segmented control. Default `Line`.
3. **Chart panel** — Plotly chart, full content width, tight-fit Y-axes, viridis palette, unified hover, PNG export.
4. **Stats footer** — for the active filter: avg pace (MM:SS), total mileage, activity count, longest run, best pace.

### 4.2 Tight Y-axis bounds

For each visible series in the rendered chart:

```
visible = [...]   # non-null values across all 12 months × all selected years
span = max(visible) - min(visible)
if span == 0: span = max(visible, 1)   # avoid zero-span for flat series
bottom = span * 0.02                   # 2% padding below min
top    = span * 0.04                   # 4% padding above max
y_min = min(visible) - bottom
y_max = max(visible) + top
```

**Pace Y-axis direction.** Pace is inverted (lower = faster). Plotly will fight `autorange: 'reversed'` against a custom `range` — they don't compose. Use a custom range with values already reversed:

```js
yaxis2: {
  range: [pace_y_max, pace_y_min],
  autorange: false,
  ...
}
```

Plotly draws axes from `range[0]` at the bottom to `range[1]` at the top, so `[max, min]` puts the largest (slowest) value at the bottom and the smallest (fastest) at the top — the desired inversion.

### 4.3 Year overlay rendering

- Years are sorted ascending before trace generation, so grouped-bar ordering is chronological.
- Each year in `[from, to]` → one Plotly trace per visible metric (pace, distance).
- Color from `Plotly.d3.scaleOrdinal(d3.schemeViridis)(years)` — perceptually uniform, colorblind-safe.
- If more than 7 years are selected, viridis pastes wrap onto the small palette — the user is warned via a small "Showing 8+ years; colors repeat" notice and can narrow the range. Recommended max selection: 6 years.
- Line widths: 2.5; markers: 6 px. Hover-highlight interaction is intentionally NOT implemented (`plotly_hover` doesn't fire on legend, and a data-point hover effect adds noise without much value). Markers + unified hover tooltip are the primary affordances.
- Distance Y on left (km), pace Y on right (MM:SS / s-per-km). `yaxis: 'y'` and `yaxis2: 'y2'`.
- If a year has all `null`s for a metric, that metric's trace is omitted for that year (no empty lines).

**Bar-mode policy.** `Bar` mode is restricted to single-year selection. If the user has 2+ years in the year range AND switches to bar, the front-end snaps the year range to the most-recent year and shows a brief toast: "Bar mode shows one year at a time — narrowed to {year}." This avoids the ambiguity of grouped bars on a dual-axis chart with two scales (pace scale and distance scale would each need their own bar grouping, and the visual is unreadable past 2 years).

**Line-mode policy.** Any number of years is allowed in line mode (recommended max 6 for color differentiation).

### 4.4 Update pipeline

```
state change (year / bucket / mode / showX)
  → applyFilters()
      derive yearValues from state
        if bucket != 'all': use monthly_by_bucket[year][bucket] instead
      compute tight bounds (see §4.2)
  → Plotly.react(document.getElementById('chart'), traces, layout, config)
  → renderStats()
```

**Zoom preservation.** `Plotly.react` re-creates the layout object, which by default resets the user's zoom/pan. To preserve interactive zoom across filter changes:

- Track user-zoom state via the `plotly_relayout` event (extract `xaxis.range[0]` / `[1]` and `yaxis.range[0]` / `[1]`).
- On a filter change (not a user-zoom event), if the user had set a custom zoom, re-apply it after the `Plotly.react` call.

If implementation gets complex, fall back to: filter changes reset zoom (`Plotly.react` with a fresh layout each time) and surface a "Reset zoom" button. Document this trade-off when implementing.

**Stats footer semantics.** Aggregates are computed over the filtered activity set (after year-range and bucket filters are applied):

- `Avg pace` = arithmetic mean of `pace_s_per_km` over filtered activities (display MM:SS).
- `Total mileage` = sum of `distance_km` over filtered activities.
- `Activity count` = number of filtered activities.
- `Longest run` = max `distance_km` over filtered activities.
- `Best pace` = min `pace_s_per_km` over filtered activities (display MM:SS).

### 4.5 Responsive

- ≥ 1024 px: control bar one row.
- 720 ≤ w < 1024 px: control bar wraps; chips shrink.
- < 720 px: control bar stacks; chart height = `min(74vh, 600px)`.

## 5. Error Handling

| Failure | Behaviour |
|---|---|
| No / missing `.env` creds | CLI raises `MissingCredentialsError`; prints path suggestions; exits 1 |
| `GarminConnectTooManyRequestsError` | Back off and retry up to 3 times (1 s, 2 s, 4 s); then print + exit 2 |
| `GarminConnectConnectionError` after retries | Print + exit 2 |
| Empty activity list | Print "No activities found"; skip JSON + HTML; exit 0 |
| All activities dropped by cleaning | Print breakdown by reason; skip JSON + HTML; exit 0 |
| `fetch('./data/garmin_activities.json')` 404 | `app.js` shows banner: "Run `uv run python get-garmin.py` to refresh data"; chart hidden |
| Corrupt JSON | `app.js` shows parse error banner |
| Filter produces all-null series | Series omitted for the affected year; chart still renders remaining years |

## 9. Acceptance criteria (for the implementation)

Implementation is "done" when **all** of the following hold:

- `uv run pytest` passes.
- `uv run python get-garmin.py` (locally with valid creds) writes `garmin_activities_formatted.xlsx` and `viz/data/garmin_activities.json` without errors.
- `git add viz/data/garmin_activities.json && git commit` works (the JSON is committed, not gitignored).
- `netlify.toml` has `publish = "viz"`.
- `python -c "import json; json.load(open('viz/data/garmin_activities.json'))"` succeeds.
- `viz/index.html` opens in a browser and:
  - Shows pace + distance as dual Y-axis by default.
  - Year-range slider filters both metrics live.
  - Distance-bucket chip filters both metrics live.
  - Line/bar toggle re-renders without full page reload.
  - In bar mode, year range is restricted to a single year.
  - Each Y-axis tight-fits within `~50 ms` of a filter change.
- Deployed Netlify page builds and serves the same UI from `/` (no 404 on `/` or `/data/garmin_activities.json`).

### First-run expectations

- On the first run against the real Garmin dataset, expect `meta.activity_count_dropped.no_pace` to be **non-empty** (likely 10–100+ entries if you imported legacy activities from older devices where `averageSpeed` was 0 or missing). This is the expected behaviour — `pace_s_per_km = None` activities are dropped under §3.3 rule #6 because they cannot contribute to a pace chart. The drop happens in `transform.normalize_activity`, where `speed_to_pace_seconds(value)` returns `None` for non-positive speed.
- If `no_pace` is unexpectedly **zero** on first run, suspect `transform.normalize_activity`'s handling of `averageSpeed` (e.g. wrong field name, missing key, field-name casing). Check that the Garmin payload actually contains `averageSpeed` keys, and that `speed_to_pace_seconds` is being called on them.
- If `no_pace` is unexpectedly equal to the **entire dataset**, suspect that `averageSpeed` is being read as a string (timezone-formatted or locale-formatted numeric). Verify `safe_float` handles the values.
- After the first run, the breakdown should be reproducible — the same dataset + same rules = same counts.

## 10. Out of scope (this round)

- Live Garmin fetch on the deployed page (security: no credentials on Netlify).
- Streaming / auto-refresh on the page (would require a backend).
- Mobile app.
- Multi-user / multi-account support.
- Heatmaps, per-route analysis, per-day analysis (could be future-phase).
- Storing historical activity data beyond what Garmin Connect already has.
- **Wrist-HR artefact filtering.** Garmin's wrist-based heart-rate sensor (no chest strap) often returns implausible values during cold-weather warm-ups or lock-on spikes. The `avg_hr` floor (30) and ceiling (230) in §3.3 catch extreme outliers but do not detect wrist-HR noise (a noisy wrist-HR reading of 47 bpm for an easy 5K passes the floor). A future phase could filter activities where `avgHeartRateSource = "wrist"` and the rolling HR curve fails a smoothness check. Not implemented this round.

### Parameters excluded from the chart (kept in JSON / Excel only)

The current chart supports `Pace` and `Distance` (with HR/duration as data-quality checks inside the pipeline). The following parameters are still extracted into `garmin_activities.json` and the Excel output for future use, but the chart UI does not currently expose them:

- Heart Rate (avg / max)
- Elevation (avg / max gain)
- Calories
- VO2 max value
- Aerobic / anaerobic training effect
- Max speed

These could be re-introduced as additional chart metrics in a future round (each would be a chart-selector chip, not a default). The JSON payload carries them so no re-fetch from Garmin is needed.

## 11. Decisions made during brainstorming

1. **Mileage-range behaviour** → filter activities by their individual distance, then re-aggregate (Activity-distance filter).
2. **Year selection** → range with overlay (one line per year on shared axes).
3. **Pace + distance display** → dual-axis overlay, each toggleable.
4. **Chart mode** → `Line | Bar` toggle, tight Y-axis bounds.
